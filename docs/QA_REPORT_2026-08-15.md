# FuelFlow FSMS — Senior QA Report

**Assessment date:** 2026-08-15  
**Build assessed:** `77cc343` (`agent/publish-fuelflow-project`)  
**Release recommendation:** **NOT READY — one high-severity release blocker**

## 1. Executive summary

FuelFlow's implemented functional slice is broadly healthy. The local six-service stack runs, both tenant and vendor authentication work, all visible tenant/vendor workspaces render against the live PostgreSQL API, the main operational backend workflow passes, responsive navigation works, and both production images build successfully.

The release gate fails because the documented backend test command is not isolated from live services. Although `phpunit.xml` declares an in-memory database, synchronous queue, and array mailer, the effective test runtime used SQLite together with the live Redis queue and configured SMTP mailer. This QA run caused 34 onboarding notification jobs to enter the live queue and fail after retry because their serialized models referenced the test SQLite connection. In another failure mode, the same configuration leak could send test notifications through a real mail account.

A second functional defect causes protected API routes to return HTTP 500 instead of 401 when an unauthenticated client does not send `Accept: application/json`. Two lower-risk quality gaps were also recorded.

## 4. Detailed findings

### QA-001 — Tests use the live Redis queue and SMTP configuration

**Severity:** High  
**Priority:** P0 / release blocker  
**Status:** Reproducible

#### Evidence

1. The documented command completed green:

   ```text
   docker compose exec -T api php artisan test --compact
   Tests: 39 passed (336 assertions)
   ```

2. A temporary diagnostic test executed inside the same PHPUnit runtime reported:

   ```json
   {"database":"sqlite","queue":"redis","mail":"smtp","cache":"array","session":"array"}
   ```

   Expected values from `phpunit.xml` were `queue=sync` and `mail=array`.

3. The queue worker processed and failed jobs immediately after the test run. The live database contained **34 failed jobs**:

   - 24 `App\Notifications\UserOnboardedNotification`
   - 10 `App\Notifications\CompanyOnboardedNotification`

4. The common failure was:

   ```text
   SQLiteDatabaseDoesNotExistException: Database file at path [fuelflow] does not exist.
   ```

   This is consistent with models serialized by the SQLite test runtime being restored by the live PostgreSQL/Redis worker.

5. [`phpunit.xml`](/D:/FSM/apps/api/phpunit.xml:30) declares the safe mail/queue drivers, but [`tests/bootstrap.php`](/D:/FSM/apps/api/tests/bootstrap.php:5) explicitly forces only database, cache, and session settings. [`VendorPlatformApiTest.php`](/D:/FSM/apps/api/tests/Feature/VendorPlatformApiTest.php:22) performs onboarding repeatedly without globally faking notifications.

#### Impact

- Running the repository's own test command pollutes the live Redis queue and `failed_jobs` table.
- Test notifications may reach a real SMTP provider if a queued payload does not fail earlier.
- A green test result hides failed asynchronous work and gives false release confidence.
- Local/test data can leak into long-running workers through serialized model references.

#### Recommended fix

1. Force `QUEUE_CONNECTION=sync` and `MAIL_MAILER=array` in `tests/bootstrap.php` before the Laravel application boots, using the same `putenv`, `$_ENV`, and `$_SERVER` pattern as the database overrides.
2. Add a permanent safety test asserting the effective database, queue, mail, cache, and session drivers.
3. Add `Notification::fake()` or `Queue::fake()` to vendor tests that are not explicitly testing delivery.
4. Run the suite while monitoring Redis and assert that its queue length does not change.
5. After the fix is verified, review and then remove/retry the 34 failed QA jobs according to the team's data-retention policy.

#### Acceptance criteria

- The diagnostic configuration is `sqlite/sync/array/array/array`.
- A full test run creates zero Redis jobs and zero new `failed_jobs` records.
- No SMTP connection is attempted during automated tests.

### QA-002 — Unauthenticated API requests can return 500 instead of 401

**Severity:** Medium  
**Priority:** P1  
**Status:** Reproducible

#### Reproduction

```text
GET /api/v1/me
Accept header omitted
Actual:   HTTP 500, "Route [login] not defined."
Expected: HTTP 401 with an API-safe error response
```

The behavior also reproduced on `/api/v1/dashboard`, `/api/v1/vendor/me`, `/api/v1/users`, and `/api/v1/audit-events`. Adding `Accept: application/json` returned the correct 401 response.

[`bootstrap/app.php`](/D:/FSM/apps/api/bootstrap/app.php:39) requests JSON rendering for `api/*`, but the authentication middleware attempts to resolve a named `login` route before exception rendering. [`routes/web.php`](/D:/FSM/apps/api/routes/web.php:5) defines no named login route.

#### Impact

- Generic API clients, uptime monitors, scanners, and malformed requests inflate the 5xx error rate.
- Authentication failures are misclassified as server faults.
- Development responses disclose avoidable framework diagnostics.

#### Recommended fix

Configure guest redirects so API routes never resolve a web login route, or explicitly render `AuthenticationException` as 401 for every `api/*` request independent of content negotiation. Add regression tests using non-JSON `get()` requests for both tenant and vendor protected routes.

#### Acceptance criteria

- Every unauthenticated `/api/*` request returns 401 regardless of `Accept` header.
- No `Route [login] not defined` exception appears in API logs.

### QA-003 — Authentication refresh effects produce lint warnings

**Severity:** Low  
**Priority:** P2  
**Status:** Confirmed by lint

Oxlint reported `react-hooks/exhaustive-deps` warnings in:

- [`ProtectedLayout.tsx`](/D:/FSM/apps/web/src/components/ProtectedLayout.tsx:21)
- [`VendorProtectedLayout.tsx`](/D:/FSM/apps/web/src/components/VendorProtectedLayout.tsx:19)

Both effects use the `currentUser` object while declaring only `currentUser.refetch` as a dependency. The current implementation worked during browser testing, but the mismatch can create a stale event handler if the query result object changes.

**Recommendation:** destructure a stable `refetch` function and reference that inside the effect, or otherwise align the effect body and dependency list. Configure CI to fail on warnings if zero-warning lint is the project policy.

### QA-004 — Critical UI flows are not protected by automated browser tests

**Severity:** Medium quality risk  
**Priority:** P2  
**Status:** Coverage gap

The frontend suite contains only 8 tests covering the API helper, formatting utilities, and `StatusBadge`. There is no committed Playwright/Cypress suite for:

- Tenant or vendor authentication and logout
- First-login password flow
- Role-based navigation and forbidden states
- User/station/vendor onboarding forms
- Purchase order, delivery, sale, and reconciliation workflows
- CSV exports/report schedules
- Desktop/mobile routing regressions

Manual QA confirmed route-level behavior in this build, but CI cannot prevent regressions in those flows.

**Recommendation:** add a minimal browser suite covering one happy path and one authorization/error path for each principal workflow, starting with both login surfaces and the order-to-reconciliation journey.

## 6. Limitations and residual risk

This was a broad release-readiness assessment, not a formal penetration, accessibility, or load test.

- A real SMTP message was not sent because the active environment is connected to an external mail provider. Notification construction/routing passed automated tests, but delivery remains unverified until QA-001 is fixed and a dedicated test recipient is approved.
- The production Compose stack was validated and both images were built, but it was not launched against external production PostgreSQL/Redis/SMTP services.
- Browser QA avoided persistent CRUD changes; backend feature tests exercised the mutating operational workflows using SQLite.
- Backup/restore, disaster recovery, sustained concurrency, large data volumes, formal WCAG conformance, and external security testing were not executed.
- ATG hardware, offline sales synchronization, secure document storage, and queued PDF/XLSX delivery remain explicitly outside the current implementation baseline.

## 7. Recommended release sequence

1. Fix QA-001 and prove a full test run produces no live queue/mail activity.
2. Fix QA-002 and add content-negotiation-independent 401 regression tests.
3. Re-run all existing quality gates, production image builds, and the tenant/vendor browser smoke suite.
4. Clear or retain the 34 QA failed jobs only after the team confirms the desired evidence-retention policy.
5. Add the initial automated end-to-end suite before the next feature release.

**Final verdict:** the implemented product workflows are promising and mostly functional, but the build should not be released while automated tests can interact with live asynchronous infrastructure.
